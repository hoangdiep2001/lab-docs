Chuẩn bị chung cho PowerShell

Ý tưởng: PowerShell 5.1 (có sẵn trên Windows) xử lý dấu nháy và file text khác Git Bash ở 3 chỗ dễ gây lỗi:
1. Truyền JSON thẳng trên dòng lệnh cho aws.exe sẽ bị PowerShell 5.1 bỏ mất dấu " bên trong, nên AWS CLI báo Invalid JSON. Cách chắc ăn nhất: ghi JSON ra file rồi truyền file://ten-file.json. AWS CLI cho phép dùng file:// cho mọi tham số kiểu chuỗi, kể cả câu query Logs Insights hay filter pattern.
2. Out-File / Set-Content -Encoding utf8 của PS 5.1 ghi thêm BOM (3 byte EF BB BF ở đầu file). Một số API sẽ báo JSON sai vì BOM. Vì vậy ta dùng [IO.File]::WriteAllText(...): hàm .NET này mặc định ghi UTF-8 không BOM.
3. [IO.File] dùng thư mục hiện tại của tiến trình, không phải thư mục bạn vừa cd trong PowerShell. Vì vậy luôn ghi đường dẫn đầy đủ "$PWD\ten-file".

# Ghi file UTF-8 KHÔNG BOM vào thư mục hiện tại
function Save-LabFile([string]$Name, [string]$Text) {
    [IO.File]::WriteAllText((Join-Path $PWD $Name), $Text)
}

# Xoá sạch 1 bucket có versioning: mọi version + delete marker, rồi xoá bucket
function Remove-LabBucket([string]$Bucket, [switch]$BypassGovernance) {
    while ($true) {
        $raw = aws s3api list-object-versions --bucket $Bucket --max-items 500 --output json
        if (-not $raw) { break }
        $v = ($raw -join "`n") | ConvertFrom-Json
        $objs = @()
        if ($v.Versions)      { $objs += $v.Versions      | ForEach-Object { @{ Key = $_.Key; VersionId = $_.VersionId } } }
        if ($v.DeleteMarkers) { $objs += $v.DeleteMarkers | ForEach-Object { @{ Key = $_.Key; VersionId = $_.VersionId } } }
        if ($objs.Count -eq 0) { break }
        Save-LabFile "delete-batch.json" (@{ Objects = $objs; Quiet = $true } | ConvertTo-Json -Depth 5)
        if ($BypassGovernance) {
            aws s3api delete-objects --bucket $Bucket --delete file://delete-batch.json --bypass-governance-retention | Out-Null
        } else {
            aws s3api delete-objects --bucket $Bucket --delete file://delete-batch.json | Out-Null
        }
    }
    aws s3api delete-bucket --bucket $Bucket
}
  • Save-LabFile: gói lại [IO.File]::WriteAllText cho gọn. Ví dụ dùng ở các lab: Save-LabFile "trust.json" @' ... '@.
  • Here-string @' ... '@: khối text nhiều dòng, không thay biến $... bên trong. Dùng @" ... "@ khi muốn PowerShell chèn biến như $ACCOUNT_ID. Dấu đóng '@ / "@ phải nằm sát lề trái, nếu thụt vào sẽ lỗi cú pháp.
  • Remove-LabBucket: aws s3 rb --force không xoá được version cũ và delete marker của bucket có versioning. Hàm này liệt kê từng lô 500 version, xoá bằng delete-objects, lặp tới khi hết rồi mới delete-bucket. Thêm -BypassGovernance cho bucket bật Object Lock chế độ GOVERNANCE (Lab 30).

Lab 26: Application Auto Scaling – ECS, DynamoDB, Lambda (D3, Task 3.2)

Bối cảnh: Application Auto Scaling là gì?

LAB.md Lab 20 đã luyện EC2 Auto Scaling (ASG). Với các dịch vụ không phải EC2, AWS dùng một dịch vụ chung tên Application Auto Scaling (CLI: aws application-autoscaling). Lab này luyện 3 loại hay ra đề: ECS service, bảng DynamoDB provisioned và Lambda provisioned concurrency. Cùng một khuôn cho mọi dịch vụ:

  1. Scalable target (register-scalable-target): khai báo "cái gì được co giãn" bằng 3 thông tin:
    - --service-namespace: ecs, dynamodb, lambda, rds, sagemaker...
    - --resource-id: định danh tài nguyên, mỗi dịch vụ một kiểu (service/<cluster>/<service>, table/<tên>, function:<tên>:<alias>).
    - --scalable-dimension: thuộc tính được đổi (ecs:service:DesiredCount, dynamodb:table:ReadCapacityUnits, lambda:function:ProvisionedConcurrency).
    - Kèm --min-capacity / --max-capacity: mọi policy chỉ được co giãn trong khoảng này.
  2. Scaling policy (put-scaling-policy): quy tắc co giãn.
    - Target tracking: giữ 1 metric quanh giá trị mục tiêu (giống điều hoà giữ 25°C). AWS tự tạo và tự quản lý CloudWatch alarm. Đây là lựa chọn mặc định.
    - Step scaling: bạn tự tạo alarm, tự định nghĩa "vượt ngưỡng bao nhiêu thì thêm bao nhiêu".
    - Predictive scaling: dự báo theo lịch sử (cần nhiều ngày dữ liệu). Có cho EC2 ASG và (từ cuối 2024) cho ECS service qua Application Auto Scaling. Không có cho DynamoDB và Lambda.
  3. Scheduled action (put-scheduled-action): đổi min/max theo giờ, dùng khi biết trước giờ cao điểm.

Cooldown: khoảng thời gian chờ sau mỗi lần co giãn để metric kịp phản ánh thay đổi, tránh co giãn liên tục. Target tracking có ScaleOutCooldown và ScaleInCooldown riêng. Trong lúc scale-out cooldown, policy không scale-in nhưng vẫn có thể scale-out tiếp nếu cần nhiều hơn. Giá trị mặc định khác nhau theo dịch vụ (cần kiểm tra bảng mặc định trong tài liệu Application Auto Scaling), nên lab này luôn ghi rõ.

Service-linked role: lần đầu register-scalable-target, AWS tự tạo role như AWSServiceRoleForApplicationAutoScaling_ECSService, ..._DynamoDBTable, ..._LambdaConcurrency. Bạn cần quyền iam:CreateServiceLinkedRole (admin đã có), không phải tự tạo role.

Phần 26a: ECS service (Fargate) với target tracking theo CPU

Ý tưởng: tạo 1 ECS service Fargate nhỏ nhất (0.25 vCPU, 0.5 GB, image nginx công khai) trong VPC mặc định, không có ALB để rẻ. Sau đó đăng ký service làm scalable target min 1, max 3 và gắn policy giữ CPU trung bình 50%. Vì nginx gần như không tốn CPU, ta sẽ tự đẩy desired lên 3 và xem target tracking tự scale-in về 1. Đó là cách quan sát policy hoạt động mà không cần tạo tải.

💸 1 task Fargate 0.25 vCPU/0.5 GB ≈ $0.012/giờ + public IPv4 $0.005/giờ. Có 3 task trong khoảng 20 phút thì vẫn chỉ vài cent. Không tạo ALB (ALB ≈ $0.0225/giờ + LCU) nên phần ALBRequestCountPerTarget chỉ đưa JSON để đọc.

Bước 1: Lấy VPC/subnet mặc định và tạo security group

$VPC_ID = aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query "Vpcs[0].VpcId" --output text
$SUBNET_IDS = (aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC_ID Name=default-for-az,Values=true `
    --query "Subnets[0:2].SubnetId" --output text) -split "\s+"
$SG26 = aws ec2 create-security-group --group-name lab26-sg --description "lab26 no inbound" `
    --vpc-id $VPC_ID --query GroupId --output text
"VPC=$VPC_ID  Subnets=$($SUBNET_IDS -join ',')  SG=$SG26"
  • describe-vpcs ... isDefault=true: lấy VPC mặc định (mỗi region có sẵn 1 cái, subnet public, tự gán IP public).
  • default-for-az=true + Subnets[0:2]: lấy 2 subnet mặc định ở 2 AZ. -split "\s+" tách chuỗi text (cách nhau bởi tab) thành mảng PowerShell.
  • create-security-group: SG mới không có inbound rule (không ai truy cập vào được), outbound mặc định mở. Task vẫn kéo được image từ internet.
  • Backtick ` ở cuối dòng: nối dòng trong PowerShell. Sau backtick không được có dấu cách.
  • Không có VPC mặc định (đã bị xoá)? Tạo lại bằng aws ec2 create-default-vpc.

Phần 26c: Lambda provisioned concurrency trên alias

Ý tưởng: provisioned concurrency (PC) giữ sẵn N môi trường Lambda đã khởi tạo, loại bỏ cold start cho API nhạy độ trễ. PC gắn với version hoặc alias, không gắn với $LATEST. Bối cảnh

LAB.md Lab 6 đã dùng một managed rule kèm remediation. Đề Professional hỏi sâu hơn: khi nào viết custom rule bằng Lambda, khi nào dùng Guard (không cần Lambda), cách triển khai cùng lúc cho cả Organization, và conformance pack khác gì một rule lẻ. Bức tranh tổng quát:

  • Config rule đánh giá CI và trả về COMPLIANT, NON_COMPLIANT hoặc NOT_APPLICABLE. Có 3 loại nguồn:
  • AWS (managed rule, ví dụ S3_BUCKET_VERSIONING_ENABLED): có sẵn, chỉ cần truyền tham số.
  • CUSTOM_LAMBDA: tự viết Lambda, gọi API PutEvaluations để trả kết quả. Linh hoạt nhất (có thể gọi API khác).

  • Trigger: configuration change (khi CI thay đổi) hoặc periodic (mỗi 1/3/6/12/24 giờ).
  • Remediation: gắn SSM Automation document vào rule, chạy tay hoặc tự động khi NON_COMPLIANT. Automation chạy bằng remediation role do bạn tạo.
  • Conformance pack: gói nhiều rule (+ remediation) trong một template YAML giống CloudFormation, triển khai và báo cáo như một khối.

Save-LabFile "index.py" @'
import json
import boto3

config = boto3.client("config")

def evaluate(ci, tag_key):
    if ci["configurationItemStatus"] in ("ResourceDeleted", "ResourceDeletedNotRecorded"):
        return "NOT_APPLICABLE", "Resource deleted"
    if ci["resourceType"] != "AWS::S3::Bucket":
        return "NOT_APPLICABLE", "Not an S3 bucket"
    tags = ci.get("tags") or {}
    if tags.get(tag_key):
        return "COMPLIANT", f"Has tag {tag_key}={tags[tag_key]}"
    return "NON_COMPLIANT", f"Missing tag {tag_key}"

def lambda_handler(event, context):
    invoking = json.loads(event["invokingEvent"])
    params = json.loads(event.get("ruleParameters") or "{}")
    tag_key = params.get("tagKey", "owner")
    msg_type = invoking["messageType"]

    if msg_type == "ConfigurationItemChangeNotification":
        ci = invoking["configurationItem"]
    elif msg_type == "OversizedConfigurationItemChangeNotification":
        summary = invoking["configurationItemSummary"]
        hist = config.get_resource_config_history(
            resourceType=summary["resourceType"], resourceId=summary["resourceId"], limit=1)
        item = hist["configurationItems"][0]
        ci = {
            "configurationItemStatus": item["configurationItemStatus"],
            "resourceType": item["resourceType"],
            "resourceId": item["resourceId"],
            "configurationItemCaptureTime": item["configurationItemCaptureTime"],
            "tags": item.get("tags", {}),
        }
    else:
        return {"skipped": msg_type}

    compliance, note = evaluate(ci, tag_key)
    config.put_evaluations(
        Evaluations=[{
            "ComplianceResourceType": ci["resourceType"],
            "ComplianceResourceId": ci["resourceId"],
            "ComplianceType": compliance,
            "Annotation": note[:256],
            "OrderingTimestamp": ci["configurationItemCaptureTime"],
        }],
        ResultToken=event["resultToken"],
    )
    return {"resource": ci["resourceId"], "compliance": compliance}
'@

Phần 27B: Custom Guard rule – bucket phải bật versioning (không Lambda)

Ý tưởng: cùng là custom rule nhưng viết bằng Guard DSL. AWS tự chạy luật trên CI. Hợp với kiểm tra thuần cấu hình. Cấu hình versioning của bucket nằm trong CI ở supplementaryConfiguration.BucketVersioningConfiguration.status (giá trị Off, Enabled, Suspended).

Bước 1: Viết luật Guard và tạo rule

}

            @{ EventSource = "aws.config"; MessageType = "OversizedConfigurationItemChangeNotification" }

Ghi nhớ cho đề thi (Lab 27):
- "Phát hiện và tự sửa cấu hình sai, ít vận hành nhất" → Config rule + remediation SSM Automation (Automatic). Sự kiện thời gian thực khác (ví dụ API call) → EventBridge + Lambda. Config thì đánh giá trạng thái cấu hình.
- Không có managed rule phù hợp: logic thuần cấu hình → Guard custom policy rule (không Lambda). Cần gọi API khác hay logic phức tạp → custom Lambda rule (PutEvaluations + ResultToken).
- Triển khai bộ rule chuẩn cho mọi account, kể cả account mới → organization conformance pack (hoặc org config rule) từ delegated admin. Xem tập trung → aggregator. Control Tower thì dùng detective controls (cũng là Config rule).
- Conformance pack vs Security Hub standard: pack là rule Config tự chọn/tùy biến, có remediation. Security Hub tổng hợp findings từ nhiều nguồn và chấm điểm theo chuẩn (CIS, FSBP).
- Config không chặn hành động (detective). Muốn chặn → SCP/RCP, IAM, CloudFormation Hooks (proactive). Config rule có proactive mode đánh giá tài nguyên trước khi tạo (qua CloudFormation Hooks), áp dụng cho một số managed rule.
- Rule không có kết quả → kiểm tra recorder đang chạy và loại tài nguyên có nằm trong recording group không.

Phần 28B: Flow Logs tới S3 dạng Parquet với custom format

Ý tưởng: CloudWatch Logs tiện truy vấn nhưng lưu lâu thì đắt. S3 + Parquet (dạng cột, nén tốt) rẻ hơn nhiều và Athena quét ít dữ liệu hơn. Custom format cho phép thêm trường hữu ích không có trong bản mặc định: vpc-id, subnet-id, instance-id, tcp-flags, pkt-srcaddr/pkt-dstaddr (IP gốc khi đi qua NAT), flow-direction, traffic-path.

$FL_BUCKET = "lab28-flowlogs-$ACCOUNT_ID"
aws s3api create-bucket --bucket $FL_BUCKET
$FMT = '${version} ${account-id} ${vpc-id} ${subnet-id} ${instance-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status} ${tcp-flags} ${pkt-srcaddr} ${pkt-dstaddr} ${flow-direction} ${traffic-path}'
$FL_S3 = aws ec2 create-flow-logs --resource-type VPC --resource-ids $VPC_ID --traffic-type ALL `
    --log-destination-type s3 --log-destination "arn:aws:s3:::$FL_BUCKET/flow/" `
    --log-format $FMT --max-aggregation-interval 60 `
    --destination-options FileFormat=parquet,HiveCompatiblePartitions=true,PerHourPartition=true `
    --query "FlowLogIds[0]" --output text
"FlowLog S3: $FL_S3"

  • --log-destination arn:aws:s3:::<bucket>/flow/: prefix flow/. Không cần role: dịch vụ log delivery tự thêm bucket policy cho delivery.logs.amazonaws.com (bạn cần quyền s3:PutBucketPolicy).
  • FileFormat=parquet: Parquet thay cho text. HiveCompatiblePartitions=true: đường dẫn dạng year=2026/month=11/... để Athena nhận partition. PerHourPartition=true: chia theo giờ, truy vấn khung giờ ngắn rẻ hơn.

✅ Kiểm tra (28B)

- Lỗi thường gặp: Access Denied for LogDestination → bucket đã có policy chặn, hoặc user thiếu quyền sửa bucket policy. Ghi chú: muốn truy vấn bằng Athena, tạo bảng với STORED AS PARQUET và partition projection (tùy chọn, không làm trong lab).

Phần 28C: Truy vấn Logs Insights

Ý tưởng: Logs Insights là ngôn ngữ truy vấn theo kiểu đường ống (pipe |): fields chọn trường → filter lọc → parse tách chuỗi thành trường → stats gom nhóm → sort → limit. Với flow log định dạng mặc định, Logs Insights tự nhận trường (srcAddr, dstAddr, dstPort, action, bytes...). Với log JSON, mọi khoá JSON cũng tự thành trường. Tính phí theo GB dữ liệu quét, nên luôn chọn khung thời gian ngắn.

Mẹo PowerShell: ghi câu query ra file rồi truyền --query-string file://... (AWS CLI cho phép file:// với mọi tham số chuỗi). Trong câu query, dùng nháy đơn 'REJECT' cho chuỗi (Logs Insights chấp nhận cả nháy đơn lẫn nháy kép).

Bước 1: Hàm chạy query và chờ kết quả

function Invoke-LabInsights([string]$LogGroup, [string]$QueryFile, [int]$Minutes = 60) {
    $end = [DateTimeOffset]::UtcNow.ToUnixTimeSeconds()
    $start = $end - ($Minutes * 60)
    $qid = aws logs start-query --log-group-name $LogGroup --start-time $start --end-time $end `
        --query-string "file://$QueryFile" --query queryId --output text
    do { Start-Sleep -Seconds 2
         $r = aws logs get-query-results --query-id $qid --output json | ConvertFrom-Json
    } while ($r.status -in @("Scheduled", "Running"))
    "Status: $($r.status)  Scanned bytes: $($r.statistics.bytesScanned)"
    $r.results | ForEach-Object { ($_ | ForEach-Object { "$($_.field)=$($_.value)" }) -join "  " }
}
  • start-query: chạy bất đồng bộ, trả queryId. --start-time/--end-time là epoch giây.
  • get-query-results: lặp tới khi status là Complete (hoặc Failed/Cancelled). bytesScanned cho biết bạn bị tính phí bao nhiêu.
  • Mỗi dòng kết quả là danh sách cặp field/value. Hàm in gọn trên một dòng.

Ghi nhớ cho đề thi (Lab 28):
- Flow log ghi metadata (IP, port, action), không ghi nội dung gói tin và không ghi một số traffic (DNS tới Route 53 Resolver, DHCP, metadata 169.254.169.254, Windows license activation...). Cần nội dung → VPC Traffic Mirroring.
- REJECT có thể do security group hoặc NACL. SG là stateful: request được phép thì response tự được phép. NACL stateless: thấy inbound ACCEPT mà outbound REJECT → nghi NACL chặn cổng ephemeral (1024–65535).
- Flow log tới CloudWatch Logs cần IAM role (deliver-logs-permission-arn). Tới S3 / Firehose dùng bucket policy hay quyền của dịch vụ log delivery, không cần role đó. Không sửa được format của flow log đã tạo, phải xoá và tạo lại.
- Lưu lâu + rẻ + truy vấn bằng SQL → flow log S3 Parquet + partition Hive + Athena. Truy vấn nhanh khi đang xử lý sự cố → CloudWatch Logs + Logs Insights.
- Logs Insights tính tiền theo dữ liệu quét: giới hạn khung thời gian và log group. Query có thể chạy trên nhiều log group (và cross-account khi bật CloudWatch cross-account observability).
- Cần metric cấp task/container cho ECS/EKS → Container Insights (ECS: cài đặt cluster/account containerInsights; EKS: add-on CloudWatch Observability). Metric mặc định của ECS chỉ ở cấp service/cluster.
- Muốn alarm từ log → metric filter (không phải Logs Insights). Muốn tìm "ai/cái gì nhiều nhất" liên tục → Contributor Insights.

Lab 29: Test action trong CodePipeline – Lambda invoke + Step Functions (D1, Task 1.2/1.4)

Bối cảnh

Task 1.2 của exam guide là "tích hợp kiểm thử tự động vào pipeline". Nhiều người nghĩ test chỉ chạy được trong CodeBuild, nhưng CodePipeline có action category Invoke để gọi Lambda hoặc Step Functions làm bước test (smoke test, integration test, kiểm tra API sau deploy). Pipeline chỉ đi tiếp khi action báo thành công.

⚠️ Lab này không dùng CodeBuild (quota CodeBuild của bạn đang chờ duyệt). Source là file zip trên S3, deploy bằng CloudFormation action. CodeBuild chỉ được nhắc như phương án thay thế.

Kiến trúc:

S3 (source.zip chứa template.yaml)
  → Stage Deploy: CloudFormation CREATE_UPDATE stack "lab29-app-stack" (Lambda lab29-app)
  → Stage Test:   [LambdaTest]  Lambda lab29-test gọi lab29-app, kiểm tra status == "ok",

  • Lambda invoke action: CodePipeline gọi Lambda bất đồng bộ với sự kiện chứa CodePipeline.job.id. Lambda bắt buộc gọi PutJobSuccessResult hoặc PutJobFailureResult. Quên gọi → action treo đến hết thời gian chờ rồi fail (cần kiểm tra timeout cụ thể của Lambda action).
  • Step Functions invoke action: CodePipeline bắt đầu một execution và chờ tới khi xong. Execution SUCCEEDED → action thành công. FAILED/TIMED_OUT/ABORTED → action fail. Không cần code gọi API kết quả. Hợp với test nhiều bước, có retry, chờ.

Lab 30: KMS grant & key policy, VPC endpoint policy, S3 Object Lock (D6, Task 6.1/6.2)

Bối cảnh

Ba chủ đề bảo vệ dữ liệu hay xuất hiện trong câu hỏi "ai được dùng khoá / bucket này, từ đâu, và có xoá được không":
- KMS: quyền dùng một customer managed key đến từ 3 nguồn: key policy (bắt buộc, là "cửa chính"), IAM policy (chỉ có tác dụng khi key policy cho phép IAM, qua statement arn:aws:iam::<account>:root), và grant (uỷ quyền tạm thời, có thể kèm điều kiện, dịch vụ AWS như EBS/RDS dùng rất nhiều). Thêm 2 điều kiện quan trọng: kms:ViaService (chỉ được dùng khoá thông qua một dịch vụ, ví dụ S3) và encryption context (cặp key/value gắn vào phép mã hoá, phải khớp khi giải mã).
- VPC gateway endpoint cho S3: traffic S3 từ VPC đi qua mạng AWS. Endpoint policy giới hạn endpoint chỉ truy cập bucket nhất định (chống rò rỉ dữ liệu sang bucket lạ). Ở chiều ngược lại, bucket policy với aws:SourceVpce buộc bucket chỉ đọc được qua endpoint.
- S3 Object Lock: WORM (ghi một lần, không sửa/xoá trong thời hạn giữ). Lab chỉ dùng chế độ GOVERNANCE.

Lab chia 3 phần độc lập. Phần 30B dùng một EC2 nhỏ (điều khiển qua SSM Run Command, không cần SSH) làm "máy bên trong VPC".

Phần 30C: S3 Object Lock – GOVERNANCE + legal hold

🚨 TUYỆT ĐỐI KHÔNG dùng chế độ COMPLIANCE trong lab. Object ở chế độ COMPLIANCE không ai xoá được hay rút ngắn thời hạn giữ, kể cả root user và AWS Support, cho tới khi hết hạn. Bucket cũng không xoá được cho tới lúc đó. Đặt nhầm 10 năm là trả tiền lưu trữ 10 năm. Lab chỉ dùng GOVERNANCE với thời hạn 10 phút.

Ý tưởng: Object Lock bảo vệ từng version object:
- Retention period (có hạn): chế độ GOVERNANCE cho phép người có quyền s3:BypassGovernanceRetention xoá sớm bằng header bypass. Chế độ COMPLIANCE thì không ai xoá được.
- Legal hold (không có hạn): bật/tắt bằng quyền s3:PutObjectLegalHold. Đang bật thì không xoá được, kể cả khi có bypass governance.
- Object Lock chỉ chặn xoá/ghi đè version. Lệnh xoá không chỉ định version vẫn tạo delete marker bình thường (dữ liệu vẫn còn).

Bước 1: Bucket bật Object Lock và object có retention

$LOCK_BUCKET = "lab30-lock-$ACCOUNT_ID"
aws s3api create-bucket --bucket $LOCK_BUCKET --object-lock-enabled-for-bucket
aws s3api get-bucket-versioning --bucket $LOCK_BUCKET
$UNTIL = (Get-Date).ToUniversalTime().AddMinutes(10).ToString("yyyy-MM-ddTHH:mm:ssZ")
$V1 = aws s3api put-object --bucket $LOCK_BUCKET --key report.txt --body .\secret.txt `
    --object-lock-mode GOVERNANCE --object-lock-retain-until-date $UNTIL `
    --checksum-algorithm SHA256 --query VersionId --output text
aws s3api get-object-retention --bucket $LOCK_BUCKET --key report.txt --version-id $V1
  • --object-lock-enabled-for-bucket: bật Object Lock khi tạo bucket. Versioning tự bật và không tắt được. Bucket cũ cũng bật được Object Lock sau này (put-object-lock-configuration), nhưng không tắt lại được.
  • --object-lock-mode GOVERNANCE --object-lock-retain-until-date: giữ version này tới thời điểm UTC 10 phút sau.
  • --checksum-algorithm SHA256: request ghi object có Object Lock bắt buộc có checksum (Content-MD5 hoặc checksum mới). CLI v2 bản mới tự thêm, ghi rõ để chạy được cả với bản cũ.

Bước 2: Thử xoá

aws s3api delete-object --bucket $LOCK_BUCKET --key report.txt --version-id $V1
aws s3api delete-object --bucket $LOCK_BUCKET --key report.txt
aws s3api list-object-versions --bucket $LOCK_BUCKET --query "{v:Versions[].[VersionId,IsLatest],dm:DeleteMarkers[].[VersionId,IsLatest]}"
aws s3api delete-object --bucket $LOCK_BUCKET --key report.txt --version-id $V1 --bypass-governance-retention
  • Lệnh 1 (xoá version cụ thể) → AccessDenied: version đang được giữ.
  • Lệnh 2 (không version) → thành công, tạo delete marker. Object "biến mất" khi GET thường nhưng version gốc còn nguyên. Đây là bẫy đề thi: Object Lock không chặn delete marker.
  • Lệnh 4 với --bypass-governance-retention → thành công vì bạn (admin) có s3:BypassGovernanceRetention. Đây là điểm khác giữa GOVERNANCE và COMPLIANCE.

Bước 3: Legal hold

$V2 = aws s3api put-object --bucket $LOCK_BUCKET --key evidence.txt --body .\secret.txt `
    --checksum-algorithm SHA256 --query VersionId --output text

  • Xoá kèm bypass vẫn AccessDenied: bypass governance không vượt được legal hold. Phải tắt hold (Status=OFF) trước.
  • Use case: điều tra pháp lý chưa biết bao giờ xong → legal hold. Quy định "giữ 7 năm" → retention (COMPLIANCE trong thực tế).

Ghi nhớ cho đề thi (Lab 30):
- KMS: key policy là bắt buộc. IAM policy chỉ có tác dụng khi key policy có statement cho account root. Cross-account: cả key policy (cho account kia) và IAM policy ở account kia.
- Dịch vụ AWS (EBS, RDS, Lambda...) cần dùng khoá thay mặt principal → grant (kms:CreateGrant + kms:GrantIsForAWSResource). Cấp quyền tạm, có thể thu hồi ngay, không sửa policy → grant (+ grant token để dùng ngay).
- "Chỉ được dùng khoá qua dịch vụ X" → kms:ViaService. "Chỉ giải mã dữ liệu của tenant/project Y" → encryption context + điều kiện kms:EncryptionContext:<key>.

- Chặn đẩy dữ liệu ra bucket ngoài từ VPC → endpoint policy của gateway endpoint. Bucket chỉ cho truy cập từ VPC → bucket policy aws:SourceVpce (một endpoint) / aws:SourceVpc (cả VPC). aws:SourceIp không dùng được với traffic qua endpoint (chỉ thấy IP private).

- WORM theo quy định, không ai xoá được → Object Lock COMPLIANCE. Cho phép người có quyền đặc biệt xoá → GOVERNANCE + s3:BypassGovernanceRetention. Không biết trước thời hạn → legal hold. Glacier dài hạn kiểu WORM → Glacier Vault Lock. Backup không xoá được → AWS Backup Vault Lock.

Phần 31B: EC2 Image Builder – container recipe → pipeline → ECR

Ý tưởng: các khối của Image Builder (giống bản AMI ở Lab 3):
- Component: tài liệu YAML (AWSTOE) mô tả các bước build/validate/test, ví dụ cài gói, ghi file cấu hình.
- Container recipe: image gốc (parent image) + danh sách component + Dockerfile template + repository ECR đích.
- Infrastructure configuration: loại EC2, instance profile, subnet/SG dùng để build.
- Distribution configuration: đẩy image tới repo ECR nào, region nào, thêm tag gì.
- Image pipeline: gắn tất cả lại, chạy tay hoặc theo lịch (có thể chỉ chạy khi image gốc/component có bản mới).

- Lỗi push ECR tag ... already exists → repo IMMUTABLE và tag trùng (thường do chạy lại cùng distribution tag).

Ghi nhớ cho đề thi (Lab 31):
- Repo ECR đầy image cũ, tốn tiền → lifecycle policy (untagged sau N ngày, giữ N image mới nhất). Luôn preview trước. Thực thi bất đồng bộ trong 24 giờ.
- Không cho ghi đè tag (truy vết được image đã deploy) → tag immutability. Deploy theo image digest (@sha256:...) là cách chắc chắn nhất.
- Quét lỗ hổng: basic (scan on push, gói OS, miễn phí) vs enhanced (Inspector, gói OS + ngôn ngữ, quét liên tục khi có CVE mới, findings sang Security Hub/EventBridge). Chặn deploy image có CVE nghiêm trọng → EventBridge bắt finding hoặc bước kiểm tra trong pipeline.
- Dùng image ở account/region khác → repository policy (cross-account pull) và replication (cross-region/cross-account). Cache image công khai (Docker Hub, ECR Public) → pull through cache.
- Tự động dựng "golden image" (AMI hoặc container) có hardening, test, phân phối nhiều region/account, chạy lại khi image gốc có bản vá → EC2 Image Builder pipeline (schedule + điều kiện dependency update). Đáp án "tự viết script trên EC2 + cron" là sai về vận hành.
- Image Builder build trên EC2 tạm điều khiển bằng SSM: instance profile cần EC2InstanceProfileForImageBuilder (+ ...ECRContainerBuilds cho container) và AmazonSSMManagedInstanceCore.

💸 Tính phí (Lab 31): ECR lưu trữ ≈ $0.10/GB-tháng (image Alpine vài MB). Basic scanning miễn phí. Enhanced scanning tính theo Inspector. Image Builder không tính phí dịch vụ, chỉ tính tài nguyên: EC2 t3.small trong lúc build (≈ $0.02/giờ), EBS tạm, log CloudWatch.
