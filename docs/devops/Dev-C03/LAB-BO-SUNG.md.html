Chuẩn bị chung cho PowerShell

Ý tưởng: Windows PowerShell 5.1 có 3 "bẫy" hay làm lệnh AWS CLI lỗi:
1. Dấu nháy kép trong JSON truyền inline bị PowerShell 5.1 nuốt mất khi gọi file .exe (aws.exe). Lỗi điển hình: Error parsing parameter '--item': Invalid JSON. Cách tránh: luôn ghi JSON ra file, rồi truyền file://ten-file.json.
2. BOM: Out-File và Set-Content -Encoding utf8 của PS 5.1 chèn 3 byte BOM vào đầu file. AWS CLI và Lambda đôi khi đọc lỗi file có BOM (Invalid JSON, hoặc Python báo SyntaxError ở dòng 1). Cách tránh: ghi bằng [IO.File]::WriteAllText(...), hàm này mặc định ghi UTF-8 không BOM.
3. Chuỗi có dấu : ngay sau biến: "$REGION:$ACCOUNT_ID" bị PowerShell hiểu $REGION: là biến có "drive" (giống $env:), nên kết quả bị rỗng. Luôn viết ${REGION}:${ACCOUNT_ID} khi biến đứng sát dấu :.

Bước 4: Đóng gói Lambda thành zip

# Trường hợp 1: chỉ có 1 file code (không thư viện ngoài)
Compress-Archive -Path .\app.py -DestinationPath .\function.zip -Force

# Trường hợp 2: có thư mục con (thư viện cài bằng pip -t)
function New-LambdaZip {
  param([string]$SourceDir, [string]$ZipPath)
  if (Test-Path $ZipPath) { Remove-Item $ZipPath }
  Push-Location $SourceDir
  try { tar.exe -a -c -f $ZipPath (Get-ChildItem -Name) } finally { Pop-Location }
}
# Ví dụ: New-LambdaZip -SourceDir "$PWD\package" -ZipPath "$PWD\function.zip"
  • Compress-Archive: đủ dùng khi zip một file ở gốc. -Force ghi đè zip cũ.
  • Tại sao cần tar.exe cho trường hợp 2: Compress-Archive của PS 5.1 (module Archive 1.0.x) ghi đường dẫn trong zip bằng dấu \. Lambda chạy Linux, nên giải nén ra file tên redis\client.py thay vì thư mục redis/, dẫn tới lỗi No module named 'redis'.
  • tar.exe -a -c -f x.zip ...: -a chọn định dạng theo đuôi file (.zip → zip), -c tạo mới, -f tên file. (Get-ChildItem -Name) truyền từng file/thư mục ở cấp gốc, để file app.py nằm ở gốc zip (Lambda tìm handler ở gốc).

Lab 23: Step Functions (D1, ưu tiên cao)

Ý tưởng / bối cảnh

AWS Step Functions là dịch vụ điều phối (orchestration) nhiều bước thành một state machine viết bằng JSON (ngôn ngữ Amazon States Language – ASL). Thay vì viết một Lambda khổng lồ tự lo retry, rẽ nhánh, chờ người duyệt... bạn khai báo các "state" và Step Functions lo phần còn lại: gọi dịch vụ, retry có backoff, bắt lỗi, lưu lịch sử từng bước.

Hai loại workflow (chọn lúc tạo, không đổi được về sau):

Standard Express
Thời gian chạy tối đa 1 năm 5 phút
Ngữ nghĩa thực thi Exactly-once (mỗi bước chạy đúng 1 lần, trừ khi bạn khai báo Retry) Async: at-least-once. Sync: at-most-once
Lịch sử thực thi Lưu trong Step Functions 90 ngày, xem Graph trên console, có API GetExecutionHistory Không có execution history API, phải bật CloudWatch Logs
.waitForTaskToken, .sync (chạy job rồi chờ) Có Không
Giá Theo state transition Theo số request + thời gian × bộ nhớ
Hợp với Quy trình nghiệp vụ dài, cần duyệt, cần audit Xử lý event số lượng lớn, IoT, stream, backend API ngắn

Express có 2 cách gọi: Asynchronous (StartExecution, trả về ngay, at-least-once) và Synchronous (StartSyncExecution, chờ có kết quả mới trả về, at-most-once, hợp để API Gateway gọi rồi trả lời client ngay).

Lab dựng một workflow "xử lý đơn hàng":

Validate (Lambda, Retry + Catch)
   └─ CheckAmount (Choice)
        ├─ amount > 100 → WaitApproval (Lambda + .waitForTaskToken: chờ người duyệt)
        └─ còn lại ────────────────┐
                                    ▼
                       SaveOrder (DynamoDB PutItem trực tiếp, KHÔNG qua Lambda)
                                    ▼
                       PostProcess (Parallel: 2 nhánh) → TagItems (Map: lặp từng item) → Done
Lỗi ValidationError / Rejected → RecordError (Pass) → OrderFailed (Fail)

Thứ tự làm: tạo bảng DynamoDB và Lambda trước (là "công cụ" mà state machine gọi) → tạo role cho Step Functions (quyền gọi các công cụ đó) → viết ASL → chạy thử từng tình huống → xem lịch sử → làm thêm một bản Express.

[IO.File]::WriteAllText("$PWD\app.py", @'
import json
from datetime import datetime, timezone


class ValidationError(Exception):
    """Lỗi nghiệp vụ: dữ liệu sai, retry cũng vô ích -> Catch."""


class TransientError(Exception):
    """Lỗi tạm thời (mạng, throttling...): nên Retry."""


def validate(event, context):
    order = event["input"]
    retry = event.get("retryCount", 0)
    print(json.dumps({"orderId": order.get("orderId"), "retryCount": retry}))
    # Giả lập lỗi tạm thời: thất bại 'failTimes' lần đầu rồi mới thành công
    if order.get("failTimes", 0) > retry:
        raise TransientError(f"Loi tam thoi gia lap o lan thu {retry}")
    if order.get("amount", 0) <= 0:
        raise ValidationError("amount phai lon hon 0")
    return {"ok": True, "attempts": retry + 1,
            "checkedAt": datetime.now(timezone.utc).isoformat()}


def notify(event, context):
    # Thực tế: gửi email/Slack cho người duyệt kèm token.
    # Lab: in token ra log; bạn sẽ tự gọi SendTaskSuccess/SendTaskFailure.
    print("APPROVAL_NEEDED", event["orderId"])
    print("TASK_TOKEN", event["taskToken"])
    return {"sent": True}
'@)
Compress-Archive -Path .\app.py -DestinationPath .\function.zip -Force
  • Exception tự định nghĩa (ValidationError, TransientError): khi Lambda ném lỗi, Step Functions lấy tên class làm tên lỗi (errorType). Nhờ vậy Retry/Catch có thể bắt theo ErrorEquals: ["TransientError"].
  • retryCount lấy từ context object $$.State.RetryCount (Bước C1), giúp giả lập "lỗi 2 lần rồi thành công" một cách xác định, không dựa vào random.
  • notify không tự trả kết quả cho workflow: với .waitForTaskToken, giá trị Lambda return bị bỏ qua. Workflow chỉ chạy tiếp khi có người gọi SendTaskSuccess/SendTaskFailure kèm đúng token.

Phần C: Viết state machine Standard

Bước C1: Định nghĩa ASL

Ý tưởng từng khối:
- Task + arn:aws:states:::lambda:invoke: gọi Lambda qua optimized integration. Kết quả trả về nằm trong Payload, nên dùng ResultSelector để chỉ lấy phần Payload.
- ResultPath: quyết định kết quả của state được gắn vào đâu trong input. "$.validation" nghĩa là giữ nguyên input gốc rồi thêm trường validation. null nghĩa là bỏ kết quả và giữ input y nguyên. Nếu không khai báo, kết quả thay thế toàn bộ input. Trong Catch, ResultPath: "$.error" giữ lại input gốc và thêm thông tin lỗi (Error, Cause).
- Retry: ErrorEquals là lỗi nào được retry, IntervalSeconds là thời gian chờ lần đầu, BackoffRate là hệ số nhân (2 → chờ 2s, 4s, 8s), MaxAttempts là số lần thử lại (không tính lần đầu). Các retrier được xét theo thứ tự.
- Catch: hết retry hoặc gặp lỗi không retry thì chuyển sang state Next.
- arn:aws:states:::dynamodb:putItem: AWS SDK/optimized integration gọi thẳng DynamoDB, không cần Lambda, nên đỡ code và đỡ tiền.

Ghi nhớ cho đề thi

  • Standard: tối đa 1 năm, exactly-once, execution history 90 ngày, tính tiền theo state transition, hỗ trợ .waitForTaskToken và .sync. Express: tối đa 5 phút, async = at-least-once (workflow phải idempotent), sync = at-most-once, tính tiền theo request + duration, log qua CloudWatch Logs. Đề hỏi "hàng chục nghìn event/giây, xử lý ngắn, rẻ" thì chọn Express. Đề hỏi "chờ con người duyệt vài ngày" thì chọn Standard + .waitForTaskToken.
  • Retry: ErrorEquals, IntervalSeconds (mặc định 1), BackoffRate (mặc định 2.0), MaxAttempts (mặc định 3; đặt 0 là không retry). Có thêm MaxDelaySeconds và JitterStrategy: FULL để chống "thundering herd". Catch: ErrorEquals + Next + ResultPath (giữ input gốc + lỗi).
  • Lỗi có sẵn: States.ALL (phải đứng cuối), States.Timeout (vượt TimeoutSeconds/HeartbeatSeconds), States.TaskFailed, States.Permissions. Với Lambda nên retry Lambda.ServiceException, Lambda.TooManyRequestsException...
  • Xử lý input/output theo thứ tự: InputPath → Parameters → (task) → ResultSelector → ResultPath → OutputPath. Muốn giữ input gốc và thêm kết quả thì dùng ResultPath. Muốn bỏ kết quả thì ResultPath: null.
  • Gọi thẳng dịch vụ (DynamoDB, SNS, SQS, EventBridge, ECS, Glue, Bedrock... và hơn 200 dịch vụ qua AWS SDK integration arn:aws:states:::aws-sdk:<service>:<action>): bớt Lambda "keo dán", bớt code, bớt chi phí.
  • 3 kiểu integration: Request Response (mặc định, gọi xong đi tiếp), Run a Job .sync (chờ job như ECS task/Glue/CodeBuild chạy xong), Callback .waitForTaskToken (chờ SendTaskSuccess/SendTaskFailure, có thể kèm SendTaskHeartbeat + HeartbeatSeconds).
  • Map có 2 chế độ: Inline (tối đa 40 iteration song song, dữ liệu từ input) và Distributed (tới 10.000 child execution song song, đọc dữ liệu từ S3, hợp với xử lý hàng triệu object). Parallel: các nhánh cố định chạy cùng lúc; một nhánh lỗi thì cả Parallel lỗi.
  • Không nên ném dữ liệu lớn qua state: payload giới hạn 256 KB. Dữ liệu lớn thì để S3 và chỉ truyền key.
  • So với EventBridge Pipes (nối nguồn → đích, có filter/enrich) và SQS (tách rời): Step Functions là điều phối có trạng thái.

Ý tưởng / bối cảnh

Cache là lớp lưu tạm dữ liệu hay đọc ở nơi truy cập nhanh hơn (bộ nhớ RAM), để giảm độ trễ và giảm tải cho database. Đề thi không hỏi "cache là gì" mà hỏi chiến lược: khi nào nạp cache, khi nào cập nhật, làm sao tránh dữ liệu cũ.

Chiến lược Cách làm Ưu điểm Nhược điểm
Lazy loading (cache-aside) Đọc: hỏi cache trước. Miss thì đọc DB rồi ghi vào cache Chỉ cache dữ liệu thật sự được đọc. Cache chết thì app vẫn chạy (chậm hơn) Lần đọc đầu luôn chậm (cache miss penalty: 3 bước). Dữ liệu có thể cũ (stale) khi DB đổi mà cache chưa đổi
Write-through Ghi: cập nhật DB và cache cùng lúc Cache luôn mới, không stale Mỗi lần ghi chậm hơn (2 nơi). Cache đầy dữ liệu không ai đọc (lãng phí), nên thường kết hợp TTL. Node cache mới thì rỗng tới khi có ghi
TTL (time to live) Mỗi key có thời hạn, hết hạn tự xoá Giới hạn thời gian stale, tự dọn rác TTL ngắn thì nhiều miss, TTL dài thì stale lâu
Invalidate khi ghi Ghi DB rồi xoá key cache, lần đọc sau lazy-load lại Đơn giản, ít stale Lần đọc ngay sau ghi bị miss

Hai vấn đề hay gặp:
- Cache stampede (thundering herd): một key "hot" hết hạn, hàng nghìn request cùng miss và cùng dội vào DB. Cách chống: lock (chỉ 1 request được nạp lại, dùng SET key NX EX), TTL có jitter (cộng thêm vài giây ngẫu nhiên để các key không hết hạn cùng lúc), hoặc làm mới trước khi hết hạn.
- Stale data: DB đổi nhưng cache còn giá trị cũ. Cách chống: write-through, invalidate khi ghi, hoặc TTL ngắn.

Bảng chọn loại cache (rất hay ra đề):

Nhu cầu trong đề Chọn Ghi chú
Cache response của REST API theo stage, không sửa code backend API Gateway cache Chỉ có ở REST API (HTTP API không có). TTL mặc định 300s, tối đa 3600s, 0 = tắt. Cache key theo path/query/header bạn chọn. Client gửi Cache-Control: max-age=0 để bỏ qua cache (cần quyền execute-api:InvalidateCache). Tính phí theo giờ theo dung lượng cache (0.5–237 GB)
Cache dữ liệu dùng chung cho nhiều service, session store, leaderboard (sorted set), pub/sub, kết quả query SQL (RDS) ElastiCache (Valkey / Redis OSS / Memcached) Phải sửa code để dùng (lazy loading / write-through). Valkey/Redis: replication, Multi-AZ, persistence. Memcached: đơn giản, đa luồng, không replication
Đọc DynamoDB cần micro-giây, nhiều lần đọc lặp lại, không muốn viết logic cache DAX API tương thích DynamoDB, chỉ đổi client. Write-through có sẵn. Chạy trong VPC
Nội dung tĩnh/động phục vụ người dùng toàn cầu, giảm tải origin CloudFront Cache ở edge. Đổi nội dung thì dùng invalidation hoặc tên file có version
Cache cấu hình/secret trong một Lambda Biến global ngoài handler, hoặc Parameters and Secrets Lambda Extension Miễn phí, nhưng mỗi execution environment có bản riêng, không chia sẻ

Lab này dựng: Lambda (trong default VPC) → ElastiCache Serverless for Valkey → DynamoDB (đi qua gateway VPC endpoint, miễn phí). Bạn sẽ thấy tận mắt MISS/HIT, độ trễ, stale data, write-through, invalidate và TTL.

Vì sao chọn ElastiCache Serverless Valkey: không phải chọn node, tạo nhanh, mức tính tối thiểu chỉ 100 MB dữ liệu (Redis OSS serverless tối thiểu 1 GB). Theo bảng giá us-east-1: khoảng $0.084/GB-giờ (mức tối thiểu 100 MB ≈ $0.0084/giờ ≈ $0.2/ngày) + $0.0023 / 1 triệu ECPU (cần kiểm tra trên trang giá AWS trước khi làm). Tức là xoá ngay sau lab thì chỉ tốn vài cent, nhưng quên xoá thì khoảng $6/tháng.
Đường rẻ hơn ($0): nếu không muốn tạo ElastiCache, đọc kỹ phần Ý tưởng, xem code ở Bước C2 (logic y hệt) và tự hình dung kết quả ở bảng Phần D. Khi đó bạn mất phần trải nghiệm VPC/security group, vốn cũng hay ra đề.

Vì sao Lambda phải nằm trong VPC: ElastiCache chỉ có endpoint private trong VPC. Lambda gắn VPC thì không có Internet và không gọi được endpoint public của AWS (ở đây là DynamoDB), trừ khi có NAT Gateway (tốn tiền) hoặc VPC endpoint. Với DynamoDB và S3 có gateway endpoint miễn phí.

Bước C2: Code Lambda

[IO.File]::WriteAllText("$PWD\app.py", @'
import json
import os
import random
import time
from decimal import Decimal

import boto3
import redis

TTL = int(os.environ.get("TTL_SECONDS", "60"))
table = boto3.resource("dynamodb").Table(os.environ["TABLE"])
# Tạo kết nối NGOÀI handler: các lần gọi "warm" dùng lại kết nối, không mất thời gian bắt tay TLS
cache = redis.RedisCluster(host=os.environ["CACHE_HOST"], port=6379, ssl=True,
                           decode_responses=True, socket_timeout=2)


def _key(pid):
    return f"product:{pid}"


def _ttl():
    return TTL + random.randint(0, 10)  # jitter: các key không hết hạn cùng một lúc


def _read_db(pid):
    time.sleep(0.3)  # giả lập DB chậm để thấy rõ khác biệt HIT/MISS
    return table.get_item(Key={"pk": pid}).get("Item")


def get_lazy(pid):
    """Lazy loading (cache-aside) + khoá chống cache stampede."""
    cached = cache.get(_key(pid))
    if cached is not None:
        return "HIT", json.loads(cached)
    got_lock = cache.set(_key(pid) + ":lock", "1", nx=True, ex=5)
    if not got_lock:  # request khác đang nạp lại -> chờ chút rồi đọc lại cache
        time.sleep(0.2)
        cached = cache.get(_key(pid))
        if cached is not None:
            return "HIT_AFTER_WAIT", json.loads(cached)
    item = _read_db(pid)
    if item:
        cache.set(_key(pid), json.dumps(item, default=str), ex=_ttl())
    cache.delete(_key(pid) + ":lock")
    return "MISS", item


def update_price(pid, price, mode):
    item = table.update_item(
        Key={"pk": pid},
        UpdateExpression="SET price = :p",
        ExpressionAttributeValues={":p": Decimal(str(price))},
        ReturnValues="ALL_NEW",
    )["Attributes"]
    if mode == "write-through":      # ghi DB và cache cùng lúc
        cache.set(_key(pid), json.dumps(item, default=str), ex=_ttl())
    elif mode == "invalidate":       # ghi DB rồi xoá key, lần đọc sau sẽ lazy-load
        cache.delete(_key(pid))
    # mode == "db-only": không đụng cache -> STALE tới khi TTL hết
    return item


def handler(event, context):
    t0 = time.perf_counter()
    op, pid = event.get("op", "get"), event.get("id", "p1")
    if op == "get":
        source, item = get_lazy(pid)
        result = {"source": source, "item": item}
    elif op == "update":
        mode = event.get("mode", "write-through")
        result = {"mode": mode, "updated": update_price(pid, event["price"], mode)}
    elif op == "ttl":
        result = {"ttlSecondsLeft": cache.ttl(_key(pid))}
    else:
        result = {"error": "op phai la get | update | ttl"}
    result["ms"] = round((time.perf_counter() - t0) * 1000, 1)
    return json.loads(json.dumps(result, default=str))
'@)
  • redis.RedisCluster(..., ssl=True): ElastiCache Serverless chạy theo cluster mode và bắt buộc TLS. Dùng client hỗ trợ cluster để tự định tuyến key tới đúng shard.
  • cache.set(key, value, ex=...): ghi kèm TTL tính bằng giây. nx=True nghĩa là chỉ ghi nếu key chưa tồn tại, chính là cách làm "khoá" chống stampede.
  • json.dumps(..., default=str): DynamoDB trả số dạng Decimal, cần đổi thành chuỗi để serialize.
  • 3 chế độ ghi write-through / invalidate / db-only giúp so sánh trực tiếp hành vi.

- Task timed out after 15.00 seconds ở lần get đầu → SG của cache chưa cho phép SG của Lambda (Bước A2), hoặc cache chưa available.
- Timeout ở _read_db (sau khi cache đã chạy) → thiếu gateway endpoint DynamoDB (Bước A3). Lambda trong VPC không ra Internet được.
- "errorType": "Runtime.ImportModuleError" ... No module named 'redis' → zip sai cấu trúc. Kiểm tra bằng tar.exe -tf function.zip | Select-Object -First 5, phải thấy app.py và redis/... ở gốc.
- AccessDeniedException ... dynamodb:UpdateItem → inline policy sai tên bảng hoặc thiếu action.

Tự làm thêm (stampede): chạy Invoke-Lab24 '{"op":"update","id":"p1","price":140,"mode":"invalidate"}' (xoá key), ghi payload.json = {"op":"get","id":"p1"} rồi gọi 10 lần bất đồng bộ cùng lúc: 1..10 | % { aws lambda invoke --function-name lab24-cache-fn --invocation-type Event --cli-binary-format raw-in-base64-out --payload file://payload.json NUL }. Sau đó xem aws logs tail /aws/lambda/lab24-cache-fn --since 5m: nhờ lock, chỉ một số ít lần gọi thực sự đọc DB.

Phần E (tuỳ chọn / đọc hiểu): DAX – "đổi client là xong"

Ý tưởng: DynamoDB Accelerator (DAX) là cache in-memory chuyên cho DynamoDB, API tương thích DynamoDB. Ứng dụng không cần viết logic lazy loading/write-through: đọc qua DAX thì DAX tự cache, ghi qua DAX thì DAX ghi xuống DynamoDB rồi cập nhật item cache (write-through). Ghi nhớ cho đề thi

  • Lazy loading: chỉ cache cái được đọc, có miss penalty, có thể stale. Write-through: không stale nhưng tốn ghi và cache chứa dữ liệu ít đọc, nên kết hợp TTL. Đề hỏi "giảm stale data" thì chọn write-through/invalidate + TTL. Đề hỏi "chỉ cache dữ liệu được yêu cầu" thì chọn lazy loading.
  • Stampede: lock (SET NX), TTL jitter, refresh sớm.
  • ElastiCache Valkey/Redis OSS: replication, Multi-AZ auto-failover, backup/snapshot, sorted set (leaderboard), pub/sub, session store. Memcached: đa luồng, đơn giản, không persistence, không replication. Serverless: không quản lý node, tính theo GB-giờ + ECPU.
  • ElastiCache/DAX nằm trong VPC. Lambda muốn dùng phải gắn VPC (cần AWSLambdaVPCAccessExecutionRole). Lambda trong VPC muốn gọi dịch vụ AWS khác thì cần VPC endpoint hoặc NAT.
  • DAX: micro-giây, tương thích API DynamoDB (không sửa logic), item cache (GetItem/BatchGetItem) và query cache (Query/Scan), TTL mặc định 5 phút. Strongly consistent read và transaction đi thẳng xuống DynamoDB, không được cache. Ghi qua DAX chỉ cập nhật item cache, query cache vẫn có thể stale tới khi TTL hết. DAX không giúp tăng tốc ghi.
  • API Gateway cache: chỉ REST API, cấp stage, TTL 300s mặc định (tối đa 3600s), có thể encrypt cache, tắt/override cache theo method, client invalidate bằng header Cache-Control: max-age=0 (nên bật "Require authorization").
  • CloudFront: cache ở edge, TTL theo cache policy / header Cache-Control, xoá bằng invalidation (tính phí sau 1.000 path/tháng) hoặc đổi tên file theo version (cách được khuyến nghị).
  • RDS đọc nhiều thì dùng ElastiCache (lazy loading) hoặc read replica. RDS Proxy là connection pooling, không phải cache.

Lab 25: CloudFront signed URL / signed cookie + OAC (D2, ưu tiên trung bình)

Ý tưởng / bối cảnh

Bài toán: website bán khoá học video. Trang giới thiệu thì ai cũng xem được, còn video/tài liệu trong private/ thì chỉ người đã mua mới xem được, và chỉ trong một khoảng thời gian. Nội dung phát qua CloudFront (CDN) cho nhanh.

Có 2 lớp bảo vệ, làm 2 việc khác nhau:
1. Origin Access Control (OAC): khoá S3 bucket để chỉ CloudFront đọc được. Người dùng không thể vào thẳng URL S3 để đi vòng qua CloudFront. CloudFront ký request tới S3 bằng SigV4. Bucket policy chỉ cho phép principal cloudfront.amazonaws.com với điều kiện AWS:SourceArn = đúng distribution của bạn. OAC thay thế OAI (legacy): OAC hỗ trợ SSE-KMS, mọi region, và cả PUT/POST.
2. Signed URL / signed cookie: khoá CloudFront để chỉ ai có chữ ký hợp lệ (do backend của bạn tạo bằng private key) mới tải được. CloudFront kiểm tra chữ ký bằng public key nằm trong một key group đã gắn vào cache behavior (trusted key groups).

Key group, không dùng root key pair: cách cũ là tạo "CloudFront key pair" bằng tài khoản root (trusted signers). AWS khuyến nghị dùng public key + key group: quản lý bằng IAM user/role thường, không cần root, mỗi key group chứa nhiều public key nên xoay vòng (rotate) dễ.

Canned policy và custom policy:
- Canned: chỉ có thời điểm hết hạn, gắn với đúng 1 URL. URL có tham số Expires, Signature, Key-Pair-Id.
- Custom: thêm thời điểm bắt đầu (DateGreaterThan), dải IP (IpAddress), và resource có wildcard. URL có tham số Policy (policy JSON mã hoá base64) thay cho Expires. Signed cookie dùng custom policy khi cần wildcard.

Thứ tự làm: bucket private → cặp khoá RSA → public key + key group → OAC → distribution (behavior mặc định công khai, behavior private/* yêu cầu chữ ký) → bucket policy → thử nghiệm.

import base64
import datetime
import sys

from botocore.signers import CloudFrontSigner
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding

domain, key_id = sys.argv[1], sys.argv[2]
with open("private_key.pem", "rb") as f:
    key = serialization.load_pem_private_key(f.read(), password=None)


def rsa_signer(message):
    return key.sign(message, padding.PKCS1v15(), hashes.SHA1())  # CloudFront RSA dùng SHA1


def cf_b64(data):  # base64 "an toàn cho URL" theo quy ước CloudFront
    return base64.b64encode(data).decode().replace("+", "-").replace("=", "_").replace("/", "~")


signer = CloudFrontSigner(key_id, rsa_signer)
expire = datetime.datetime.now(datetime.timezone.utc) + datetime.timedelta(minutes=10)
policy = signer.build_policy(f"https://{domain}/private/*", expire).encode()  # custom policy có wildcard
print(f"CloudFront-Policy={cf_b64(policy)}; "
      f"CloudFront-Signature={cf_b64(rsa_signer(policy))}; "
      f"CloudFront-Key-Pair-Id={key_id}")
'@)

Ghi nhớ cho đề thi

  • OAC (khuyến nghị) thay OAI (legacy): bucket policy cho principal cloudfront.amazonaws.com + điều kiện AWS:SourceArn. OAC hỗ trợ SSE-KMS (phải cho CloudFront quyền kms:Decrypt trong key policy), mọi region, PUT/DELETE.
  • Đề hỏi "chặn người dùng truy cập thẳng S3, chỉ qua CloudFront" thì đáp án là OAC + bucket policy. Đề hỏi "chỉ người trả tiền mới xem được" thì đáp án là signed URL/cookie.
  • Nhiều file / không muốn đổi URL / streaming HLS → signed cookie. 1 file / client không hỗ trợ cookie → signed URL. Nếu request có cả hai thì CloudFront dùng signed URL.
  • Key group + public key (IAM quản lý, tối đa 4 key group trên mỗi behavior, cần kiểm tra con số) thay vì CloudFront key pair (chỉ root tạo được, legacy).
  • Canned policy: chỉ có hết hạn, URL ngắn hơn. Custom policy: thêm start time, IP, wildcard, và có thể dùng lại cho nhiều file.
  • S3 presigned URL khác hẳn: ký bằng IAM, đi thẳng S3, thời hạn tối đa 7 ngày (IAM user, SigV4). Ký bằng role thì hết hạn theo session.
  • Bảo vệ origin custom (ALB/EC2): dùng custom header bí mật + WAF, hoặc VPC origin. OAC chỉ dành cho S3/Lambda URL/MediaStore/MediaPackage.
  • Field-level encryption: mã hoá riêng một vài trường form ở edge bằng public key (ít gặp, chỉ cần biết tên).

Lab 26: IAM Identity Center + CLI profile và credential provider chain (D2 – 2.1.1, 2.1.3, ưu tiên trung bình)

Ý tưởng / bối cảnh

Vấn đề: dev hay để access key dài hạn (IAM user) trong ~/.aws/credentials. Key lộ (commit nhầm lên Git, máy bị nhiễm mã độc) là mất tài khoản. IAM Identity Center (tên cũ: AWS SSO) cho người dùng đăng nhập một lần qua trình duyệt, rồi CLI/SDK nhận credential tạm thời (STS) của một role trong tài khoản AWS. Credential tự hết hạn, không còn key dài hạn trên máy.

Các khái niệm:
- Instance của Identity Center có 2 loại:
- Organization instance: bật trong management account của AWS Organizations. Chỉ loại này mới cấp được quyền truy cập vào AWS account (permission set, account assignment).
- Account instance: gắn với một account đơn lẻ, chỉ dùng cho một số ứng dụng AWS (ví dụ Amazon Q Developer). Nó không có permission set và không cấp được quyền vào AWS account. Đây là bẫy hay gặp: bật nhầm account instance thì không làm được lab này.
- User/Group: danh tính trong identity store (thư mục có sẵn của Identity Center, hoặc nối với Entra ID/Okta/AD).
- Permission set: "khuôn quyền" (managed/inline policy + thời hạn session). Khi gán (account assignment) cho user ở một account, Identity Center tự tạo IAM role AWSReservedSSO_<tên>_<hash> trong account đó.
- AWS access portal (https://d-xxxxxxxxxx.awsapps.com/start): trang đăng nhập. CLI dùng URL này trong aws configure sso.

Đường làm với chỉ 1 tài khoản: biến tài khoản hiện tại thành management account của một Organization mới (miễn phí, không cần thêm account nào), bật organization instance, rồi gán permission set cho chính account này.

⚠️ Nếu tài khoản của bạn đang là member account trong Organization của công ty, bạn không tự tạo organization instance được. Khi đó chỉ làm Phần E (profile, credential_process, thứ tự ưu tiên), còn phần còn lại đọc để hiểu.

Phần B: API Gateway WebSocket API

Ý tưởng / bối cảnh

REST/HTTP API theo kiểu request–response: client hỏi thì server mới trả lời. Ứng dụng chat, thông báo realtime hay game cần server chủ động đẩy dữ liệu xuống client. WebSocket API giữ một kết nối 2 chiều lâu dài, mỗi kết nối có một connectionId.
- Route đặc biệt: $connect (khi client kết nối; có thể dùng authorizer ở đây để chặn), $disconnect (khi ngắt; chỉ là best-effort), $default (khi không khớp route nào).
- Route selection expression: API đọc trường nào trong message để chọn route. Ví dụ $request.body.action: message {"action":"sendmessage",...} sẽ đi vào route sendmessage.
- Server đẩy xuống client: backend gọi POST https://{api-id}.execute-api.{region}.amazonaws.com/{stage}/@connections/{connectionId} (API apigatewaymanagementapi). Ngoài ra còn GET (thông tin kết nối) và DELETE (ngắt kết nối). Muốn gọi thì cần quyền IAM execute-api:ManageConnections.

Thứ tự làm: tạo API (để có API_ID) → role Lambda có quyền ManageConnections trên đúng API → Lambda → integration → các route → cho API Gateway quyền gọi Lambda → deploy stage → test bằng wscat → đẩy tin từ CLI.

import json

import boto3


def handler(event, context):
    rc = event["requestContext"]
    route, cid = rc["routeKey"], rc["connectionId"]
    print(json.dumps({"route": route, "connectionId": cid}))

    if route in ("$connect", "$disconnect"):
        return {"statusCode": 200}  # $connect trả khác 200 -> từ chối kết nối

    # Endpoint quản lý kết nối: https://{domain}/{stage}
    api = boto3.client("apigatewaymanagementapi",
                       endpoint_url=f"https://{rc['domainName']}/{rc['stage']}")
    if route == "sendmessage":
        body = json.loads(event.get("body") or "{}")
        reply = {"echo": body.get("message"), "yourConnectionId": cid}
    else:  # $default
        reply = {"error": 'Khong ro action. Gui {"action":"sendmessage","message":"..."}'}
    api.post_to_connection(ConnectionId=cid, Data=json.dumps(reply).encode("utf-8"))
    return {"statusCode": 200}
'@)

  • add-permission: resource-based policy trên Lambda cho phép API Gateway (đúng API này) gọi hàm. Thiếu nó thì client kết nối bị từ chối (502 / Internal server error).

✅ Kiểm tra kết quả (Phần B)
- Cửa sổ wscat nhận được {"notice":"Server day tin qua @connections"} mà không cần gửi gì trước. Đây chính là server push.
- Log Lambda có các dòng "route": "$connect", "sendmessage", "$default", "$disconnect".
- Chạy post-to-connection sau khi đã ngắt → lỗi GoneException (HTTP 410): kết nối không còn tồn tại.

Lỗi thường gặp
- wscat báo Unexpected server response: 403 → sai URL/stage (thiếu /dev), hoặc chưa deploy.
- Unexpected server response: 500/502 khi connect → thiếu add-permission, hoặc Lambda lỗi ở $connect (xem log).
- Gửi sendmessage nhưng không nhận gì, log có AccessDeniedException ... ManageConnections → policy ws-manage sai API_ID.
- npx không có → cài Node.js LTS từ nodejs.org rồi mở lại PowerShell.

Ghi nhớ cho đề thi

  • Amplify Hosting: mỗi branch = một môi trường có URL riêng. Biến môi trường override theo branch. PR previews. Branch auto-detection theo pattern. Password protect theo branch. Build theo amplify.yml. Đề hỏi "frontend SPA/Next.js cần CI/CD + môi trường theo branch nhanh nhất" thì chọn Amplify.
  • WebSocket API: route $connect / $disconnect / $default + route tuỳ chỉnh theo routeSelectionExpression (thường $request.body.action). Authorizer (Lambda/IAM) chỉ gắn ở $connect.
  • Backend đẩy tin bằng POST @connections/{connectionId} (quyền execute-api:ManageConnections). Client đã ngắt thì nhận GoneException 410, lúc đó nên xoá connectionId khỏi bảng (thường lưu connectionId trong DynamoDB ở $connect).
  • Giới hạn cần biết: kết nối WebSocket tối đa 2 giờ, idle timeout 10 phút, mỗi message tối đa 128 KB (frame 32 KB). Cần kiểm tra lại các con số này trên trang quotas trước khi thi.
  • Realtime với GraphQL subscription thì chọn AppSync. Realtime với WebSocket "thuần" + Lambda thì chọn API Gateway WebSocket API.
