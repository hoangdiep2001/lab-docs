Bước 3: Viết hook hooks/pre_traffic.py

CodeDeploy gọi hàm này trước khi chuyển alias live sang version mới. Hàm phải báo kết quả về CodeDeploy: Succeeded thì chuyển traffic, Failed thì dừng và giữ nguyên bản blue.

import json
import os

import boto3

codedeploy = boto3.client("codedeploy")
lambda_client = boto3.client("lambda")


def lambda_handler(event, context):
    status = "Failed"
    try:
        # Gọi thẳng version mới (green), lúc này user chưa ai gọi tới nó
        resp = lambda_client.invoke(FunctionName=os.environ["NEW_VERSION"], Payload=b"{}")
        payload = json.loads(resp["Payload"].read())
        print("Smoke test:", payload)
        if "FunctionError" not in resp and payload.get("statusCode") == 200:
            status = "Succeeded"
    except Exception as e:
        print("Loi:", e)

    print("Bao CodeDeploy:", status)
    codedeploy.put_lifecycle_event_hook_execution_status(
        deploymentId=event["DeploymentId"],
        lifecycleEventHookExecutionId=event["LifecycleEventHookExecutionId"],
        status=status,
    )

2x-c. ECS blue/green: native (2025) và CodeDeploy (cách cũ)

Cách 1: ECS built-in blue/green (từ 07/2025, không cần CodeDeploy). Làm trên console với service ECS có ALB:

  1. ECS → service → Update → Deployment options → Deployment strategy: Blue/green.
  2. Chọn production listener rule và test listener rule (tuỳ chọn), 2 target group (hiện tại và alternate), và role cho ECS sửa ALB.
  3. Đặt Bake time (ví dụ 5 phút): thời gian giữ cả blue và green sau khi chuyển 100% traffic, để rollback ngay nếu có lỗi.
  4. Thêm Lifecycle hook (Lambda) ở giai đoạn POST_TEST_TRAFFIC_SHIFT để chạy smoke test trên green qua listener test. Lambda trả FAILED thì ECS rollback.
  5. Gắn CloudWatch alarm (ví dụ 5XX của target group) để tự rollback trong bake time.

Các giai đoạn của native blue/green (hook gắn vào được): RECONCILE_SERVICE → PRE_SCALE_UP → SCALE_UP → POST_SCALE_UP → TEST_TRAFFIC_SHIFT → POST_TEST_TRAFFIC_SHIFT → PRODUCTION_TRAFFIC_SHIFT → POST_PRODUCTION_TRAFFIC_SHIFT → BAKE_TIME → CLEAN_UP.

Trong API/CloudFormation: deploymentController.type = ECS, deploymentConfiguration.strategy = BLUE_GREEN, bakeTimeInMinutes, lifecycleHooks[], alarms, và loadBalancers[].advancedConfiguration (alternate target group, listener rule, role).

Bài tập tính RCU/WCU (phải đúng 10/10)

1 RCU = 1 lần đọc strongly consistent mỗi giây cho item ≤ 4 KB (eventually consistent thì 1 RCU đọc được 2 lần; transactional tốn gấp đôi).
1 WCU = 1 lần ghi mỗi giây cho item ≤ 1 KB (transactional tốn gấp đôi). Kích thước item luôn làm tròn lên.

# Đề Đáp án
1 10 lần đọc/giây, item 6 KB, strongly consistent ⌈6/4⌉=2 × 10 = 20 RCU
2 Như câu 1 nhưng eventually consistent 20 / 2 = 10 RCU
3 Như câu 1 nhưng transactional 20 × 2 = 40 RCU
4 5 lần ghi/giây, item 2.5 KB ⌈2.5⌉=3 × 5 = 15 WCU
5 5 lần ghi/giây transactional, item 2.5 KB 30 WCU
6 100 lần đọc/giây eventually consistent, item 1 KB 1 × 100 / 2 = 50 RCU
7 20 lần ghi/giây, item 512 B 20 WCU
8 1 lần đọc/giây strongly consistent, item 9 KB ⌈9/4⌉ = 3 RCU
9 60 lần đọc/phút strongly consistent, item 4 KB 1/giây → 1 RCU
10 3 lần ghi/giây, item 3.1 KB 4 × 3 = 12 WCU

Ghi nhớ cho đề thi:
- Partition key nên có nhiều giá trị khác nhau (high cardinality) để tránh hot partition. Lỗi ProvisionedThroughputExceededException xử lý bằng exponential backoff (SDK đã tự làm sẵn).
- LSI: chỉ tạo được lúc tạo bảng, dùng cùng partition key, hỗ trợ strongly consistent.
- GSI: tạo được bất cứ lúc nào, chỉ eventually consistent, có throughput riêng.
- Query nhanh hơn Scan. FilterExpression không giảm RCU tiêu thụ. Muốn Scan nhanh hơn thì dùng parallel scan (Segment/TotalSegments). Phân trang bằng LastEvaluatedKey.
- Muốn chống ghi đè thì dùng conditional write hoặc optimistic locking (thuộc tính version). Cần ghi nhiều item theo kiểu tất cả hoặc không gì cả thì dùng TransactWriteItems.

  3. Caching: bật cache trên stage của API Gateway (TTL 60 giây), so sánh latency trong CloudWatch (CacheHitCount).

import base64, json
def handler(event, context):
    for r in event["Records"]:
        data = json.loads(base64.b64decode(r["kinesis"]["data"]))   # data trong event là base64
        if data["n"] == 13:

Bước 3: Firehose (không viết consumer). Console Amazon Data Firehose → Create: source = Kinesis stream lab14, destination = S3 bucket mới, buffer 60 giây / 1 MB, bật Transform with Lambda (tuỳ chọn), định dạng nén GZIP. Gửi thêm vài record, sau khoảng 1 phút xem object trong S3.

Bước 4: On-demand mode.

aws kinesis update-stream-mode --stream-arn arn:aws:kinesis:$REGION:$ACCT:stream/lab14 \
  --stream-mode-details StreamMode=ON_DEMAND

Ghi nhớ cho đề thi:
- Mỗi shard: ghi 1 MB/s hoặc 1,000 record/s; đọc 2 MB/s chia cho mọi consumer. Nhiều consumer cần đọc riêng: enhanced fan-out (2 MB/s mỗi consumer, push qua SubscribeToShard).
- ProvisionedThroughputExceededException ở producer: partition key không đều (hot shard) → dùng key có nhiều giá trị, retry với backoff, thêm shard (resharding) hoặc chuyển on-demand. KPL gộp nhiều record nhỏ (aggregation) để tăng throughput.
- Lambda ESM với Kinesis: ParallelizationFactor (1–10 batch song song mỗi shard, vẫn giữ thứ tự theo key), BisectBatchOnFunctionError, MaximumRetryAttempts, MaximumRecordAgeInSeconds, on-failure destination (SQS/SNS). Metric chính: IteratorAge.
- KCL: checkpoint lưu trong DynamoDB, số worker hữu ích tối đa = số shard.
- Kinesis Data Streams (real-time, tự viết consumer, đọc lại được) và Firehose (gần real-time, buffer 0–900 giây, tự giao tới S3/Redshift/OpenSearch/HTTP, transform bằng Lambda, không đọc lại được). Cần hàng đợi việc, mỗi message một consumer: SQS.

export class Lab16Stack extends cdk.Stack {

    super(scope, id, props);
    const table = new dynamodb.Table(this, 'Orders', {
      partitionKey: { name: 'pk', type: dynamodb.AttributeType.STRING },
      billingMode: dynamodb.BillingMode.PAY_PER_REQUEST,
      removalPolicy: cdk.RemovalPolicy.DESTROY,          // lab: cho phép xoá bảng khi destroy
    });
    const fn = new lambda.Function(this, 'Fn', {
      runtime: lambda.Runtime.PYTHON_3_12,
      handler: 'index.handler',
      code: lambda.Code.fromInline('def handler(e, c):\n    return {"statusCode": 200, "body": "ok"}'),
      environment: { TABLE: table.tableName },
    });
    table.grantReadWriteData(fn);                         // tự sinh IAM policy least privilege
    new apigw.LambdaRestApi(this, 'Api', { handler: fn }); // L3-ish pattern: API + proxy
  }
}

Lab 21: SDK practice: retry, paginator, waiter, SigV4, serialize (D1 Task 1.1.5 / 1.1.7, D2 2.1.5)

# sdk_lab.py  (chạy: python sdk_lab.py)
import base64, json, boto3
from botocore.config import Config
from boto3.dynamodb.types import TypeSerializer, TypeDeserializer

# 1) Retry mode: legacy (mặc định cũ) / standard / adaptive (thêm rate limit phía client)
cfg = Config(retries={"mode": "adaptive", "max_attempts": 8}, connect_timeout=3, read_timeout=10)
s3 = boto3.client("s3", config=cfg)

# 2) Paginator: list_objects_v2 chỉ trả tối đa 1,000 key mỗi lần
count = 0
for page in s3.get_paginator("list_objects_v2").paginate(Bucket="<bucket-co-nhieu-object>"):
    count += len(page.get("Contents", []))
print("objects:", count)

# 3) Waiter: chờ tài nguyên sẵn sàng thay vì tự viết vòng lặp sleep
ddb = boto3.client("dynamodb", config=cfg)
ddb.create_table(TableName="lab21", BillingMode="PAY_PER_REQUEST",
                 AttributeDefinitions=[{"AttributeName": "pk", "AttributeType": "S"}],
                 KeySchema=[{"AttributeName": "pk", "KeyType": "HASH"}])
ddb.get_waiter("table_exists").wait(TableName="lab21")

# 4) Serialize: client cấp thấp cần định dạng {"S": ...}, {"N": "..."}
item = {"pk": "u1", "age": 30, "tags": ["a", "b"]}
low = {k: TypeSerializer().serialize(v) for k, v in item.items()}
print(low)                                    # {'pk': {'S': 'u1'}, 'age': {'N': '30'}, 'tags': {'L': [...]}}
ddb.put_item(TableName="lab21", Item=low)
back = {k: TypeDeserializer().deserialize(v) for k, v in ddb.get_item(TableName="lab21", Key={"pk": {"S": "u1"}})["Item"].items()}
print(back)                                   # số trả về dạng Decimal, cần chuyển khi json.dumps

# 5) Base64: Kinesis data và body nhị phân của API Gateway (isBase64Encoded=true)
print(base64.b64decode(base64.b64encode(json.dumps(item).encode())).decode())

Gọi API Gateway có IAM auth bằng SigV4 từ terminal (đổi method ở Lab 15 sang Authorization: AWS_IAM):

curl -s "https://<api-id>.execute-api.$REGION.amazonaws.com/dev/orders" \
  --aws-sigv4 "aws:amz:$REGION:execute-api" \
  --user "$AWS_ACCESS_KEY_ID:$AWS_SECRET_ACCESS_KEY" \
  -H "x-amz-security-token: $AWS_SESSION_TOKEN"      # bỏ dòng này nếu dùng access key dài hạn

Ghi nhớ cho đề thi:
- Retry: SDK đã retry sẵn với exponential backoff + jitter. Standard mode retry cả lỗi throttle/transient; adaptive thêm giới hạn tốc độ phía client. Vẫn còn lỗi thì tăng max_attempts hoặc xử lý throttle ở thiết kế.
- Paginator cho API trả nhiều trang (NextToken, ContinuationToken, LastEvaluatedKey). Waiter để chờ trạng thái (table_exists, instance_running, stack_create_complete).
- SigV4: ký request bằng access key + secret (+ session token nếu là credential tạm). Lỗi SignatureDoesNotMatch / Signature expired thường do sai secret hoặc đồng hồ máy lệch quá 5 phút.
- CLI v2 truyền blob: --cli-binary-format raw-in-base64-out. Credential chain: env var → ~/.aws profile (cả SSO) → container role → instance profile.
